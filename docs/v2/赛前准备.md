    4.1 当前方案（YOLOv8 + DeepSORT）：我的系统现在能做到什么水平？
        【检测端 — YOLOv8】
        - 模型规模：本项目使用 YOLOv8s（或根据实际填写 n/s/m/l/x），参数量约 11.1M（s），模型文件约 22MB
        - mAP (COCO)：YOLOv8s 约 44.9% mAP50-95；在自有细胞数据集上微调后需实测
        - 推理速度：单帧约 2-5ms (GPU) / 30-80ms (CPU)，取决于模型规模和输入分辨率
        - 输出内容：目标的边界框（x,y,w,h）、类别、置信度；本项目同时支持实例分割（mask）
        【跟踪端 — DeepSORT】
        - 核心机制：卡尔曼滤波预测轨迹位置 + 128 维 CNN 外观特征提取 + 匈牙利匹配
        - MOTA：在通用 MOT 数据集上约 61-70%；在细胞数据上需实测
        - IDF1：通用场景约 62%；本场景因细胞外观高度相似，外观特征区分度有限，IDF1 可能偏低
        - ID Switch：通用 MOT16 上约 781 次；细胞场景下因同种细胞外观相似、密集分布，ID 切换风险更高
        - 速度：约 40 FPS (Python)，瓶颈主要在 ReID CNN 特征提取
        【资源占用】
        - GPU 显存：YOLO 模型约 0.5-2GB + DeepSORT ReID 约 0.2GB ≈ 总计 1-3GB
        - RAM：正常推理约 4-6GB，大视频帧缓存可能需要更多
        - 存储：单次任务输出包括标注视频（MP4）、CSV/JSON 数据文件、帧图片
        >> 答辩前必须做的：用项目实际跑的 1-2 个细胞视频，实测并记录以上指标。建议整理为一张 A4 表格，左侧是”指标名称”，中间是”本系统实测值”，右侧是”对比基准/行业水平”。

          a) 外观特征（128 维 CNN）在行人数据上训练，对显微镜细胞图像泛化能力存疑

          c) 级联匹配依赖手动调节 λ（运动 vs 外观权重），最优参数在不同细胞类型间可能不同
        - 后续可替换方向：ByteTrack（不依赖外观特征，对细胞场景天然更友好）

    4.3 改进方向与决策逻辑：我后续打算怎么改？为什么这么选？
        —— 详见 `改进方向与技术路线.md`，以下为答辩时需能口头阐述的核心内容 ——

        【方向一：YOLOv8 → YOLOv11（最高优先级，短期）】
        问题：YOLOv8 对密集小细胞检测不够精细，偶尔漏检
        → 方案：升级到 YOLOv11，同 Ultralytics 框架下换权重即可
        → 为什么选 YOLOv11 而不是 v12？
           - YOLOv12 是社区版，注意力中心化架构虽精度更高，但 CPU 推理慢、显存占用大，不适配本项目”普通硬件可运行”的定位
           - YOLOv11 参数减少 22%，同精度下模型更轻量，C2PSA 空间注意力对密集小细胞检测提升明显
           - 完全兼容现有 Ultralytics 代码，改动极小
        → 预期效果：细胞检测 mAP 提升 1-3%，密集细胞漏检减少，模型文件更小

        【方向二：DeepSORT → ByteTrack（最高优先级，短期）】
        问题：DeepSORT 的 ReID 外观特征在同种细胞（外观高度相似）场景下区分度低，且额外占用 GPU 显存
        → 方案：替换为 ByteTrack，保留低置信度检测框进行二次匹配
        → 为什么选 ByteTrack 而不是 OC-SORT/BoT-SORT？
           - 细胞视频通常固定机位拍摄（无相机运动），BoT-SORT 的相机运动补偿用不上
           - 如果细胞运动较规则（贴壁细胞缓慢迁移），ByteTrack 的卡尔曼预测已足够，OC-SORT 的 ORU 回溯修正收益不大
           - ByteTrack 无需 ReID 模型，省 GPU 显存，部署更轻量
           - 如果细胞运动不规则/频繁交叉 → 再考虑升级到 OC-SORT
        → 预期效果：MOTA 提升 10-16%，ID 切换减少，显存占用降低约 0.2GB

        【方向三：OC-SORT 作为备选（高优先级，中期）】
        触发条件：ByteTrack 在细胞遮挡/交叉场景下 ID 切换仍然偏高
        → 方案：切换到 OC-SORT，利用 ORU 回溯修正遮挡期间轨迹漂移
        → 为什么不一上来就用 OC-SORT？
           - ByteTrack 更简单、更轻量，满足大部分场景
           - 先验证简单方案，有明确问题再升级复杂方案——这是工程优化的基本原则
        → 预期效果：遮挡后重识别更准，轨迹更平滑，IDF1 进一步提升

        【方向四：HFM-Tracker 条件启用（高优先级，长期）】
        当前状态：核心算法已在本项目中实现完成
        为什么暂未启用？
           - C 扩展编译问题：环形卷积、Level Set、ACM 代价计算依赖 C/C++ 底层实现，需为 Windows/macOS/Linux 分别编译 .dll/.dylib/.so
           - 硬件门槛：CA 轮廓检测 + Level Set 后处理计算量大，推荐 32GB RAM
           - 项目理念：面向科研人员，”一键安装、Web 操作、无需编译环境”是核心设计目标
        不是不做，是等工程条件成熟——预编译好各平台动态库、降低硬件门槛后，以前端下拉选项形式提供给用户
        → 短期替代验证方式：先在本地开发环境（不通过 Web）用 HFM-Tracker 在自己细胞视频上跑出结果，答辩时可以展示对比效果截图

        >> 答辩时如果被追问”你怎么证明升级方向是对的？”——最佳回应是拿出自己数据集上的对比实验结果。
           建议至少做一组：YOLOv8+DeepSORT vs YOLOv11+ByteTrack，在自己的 1-2 个细胞视频上对比 MOTA、ID Switch、耗时。

    4.5 答辩高频追问——建议逐条准备好 30 秒口头回答
        Q1：”你的系统和现成的 ImageJ/TrackMate 插件有什么区别？为什么要做 Web 版？”
        → 要点：ImageJ 需要本地安装、手动配置、有学习曲线；本系统基于 Web，上传视频→点按钮→出结果，
           进度实时推送，自由绘图模块支持 Python 代码自定义分析——目标用户是不想学命令行/编译的科研人员。

        Q2：”DeepSORT 是 2017 年的方法，你为什么不用更新的？”
        → 要点：DeepSORT 是最成熟稳定的 baseline，优先保证系统可运行；后续升级方向已明确（ByteTrack/YOLOv11），
           且改进方案已纳入 `改进方向与技术路线.md`，这是有意识的工程决策而非不了解前沿。

        Q3：”你说 HFM-Tracker 实现了，具体实现了哪些部分？代码在哪？”
        → 要点：核心算法逻辑（CA 轮廓注意力 + ACM 自适应混淆矩阵 + 两阶段匹配）已用 Python 复现；
           未集成到 Web 服务的原因是 C 扩展加速层需预编译（环形卷积/Level Set 在纯 Python 下太慢），
           且项目面向科研人员需保证”一键安装”体验。当前可本地命令行运行，Web 集成待工程条件成熟。

        Q4：”你怎么评价你的追踪结果好不好？用什么指标？”
        → 要点：MOTA（综合跟踪准确度）、IDF1（身份保持能力）、ID Switch（身份切换次数）、
           MOTP（定位精度）。对于细胞追踪，还需关注分裂检测的准确性。
           本系统在结果页面展示的统计数据和可视化图表（轨迹图、速度分布等）也是对追踪质量的间接呈现。

        Q5：”你的方法对不同的细胞类型、不同的显微镜（明场/荧光/相差）能通用吗？”
        → 要点：YOLOv8 作为通用检测器，在多种图像模态上都有较好的泛化能力，但需要针对具体细胞类型微调；
           HFM-Tracker 论文在明场 MCF-7 细胞上验证，换其他细胞类型需重新训练/调参；
           这是目前细胞追踪领域的共性问题（CTC 比赛也按数据集分别排名），不是本项目独有的局限。

        Q6：”你的项目最大的技术贡献是什么？”
        → 要点：(1) 将 YOLO+DeepSORT 的通用追踪流程工程化为一个完整的、科研人员可直接使用的 Web 系统；
           (2) 自由绘图模块让不写代码的科研人员也能用 Python 做自定义数据分析；
           (3) 预研并实现了 HFM-Tracker 细胞专用追踪算法，为后续升级铺平了道路；
           (4) 对领域前沿有系统调研和明确的改进路线图（参见 `改进方向与技术路线.md`）。
